# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Build the Requester-facing application using a temporary Development Requester identity to create IT support tickets, view own tickets, view ticket details, and manage attachments.

## 2. Stakeholder Request Interpretation
Create a responsive ticketing experience for Requesters. Requesters can submit tickets with categories, systems, priority, and attachments. After submission, they can find their tickets, view details, and manage attachments. A temporary "Development Requester" selector is used for testing user context until real authentication is added in Lab 3. We must establish a consistent Zen Green Theme.

## 3. Scope
### Included
- Development Requester selection and context management
- Create Ticket workflow (form, validation, submission)
- My Tickets workflow (paginated list, search, filter, sort)
- Requester Ticket Detail (view ticket details)
- Attachment lifecycle (upload, download, soft-remove)

### Excluded
- Real authentication (login, logout, passwords, sessions)
- IT Staff workflow (dashboard, claiming tickets, changing IT Priority)
- Ticket collaboration (Public Comments, Internal Notes, Actions Taken)
- Ticket lifecycle beyond "New" status (resolution, closing, etc.)
- Administration functions

## 4. Functional Requirements
- FR-01: The system shall allow the user to select an active Development Requester to simulate login.
- FR-02: The system shall allow the selected Requester to submit a new ticket with required fields and optional attachments.
- FR-03: The system shall display a list of tickets owned by the currently selected Requester (My Tickets) with search, filter, sort, and pagination.
- FR-04: The system shall prevent a Requester from viewing tickets belonging to other Requesters.
- FR-05: The system shall allow the Requester to view details of their own tickets.
- FR-06: The system shall allow the Requester to upload up to 5 valid attachments per ticket.
- FR-07: The system shall allow the Requester to soft-remove their own attachments.

## 5. Business Rules
- BR-01: The official Ticket Number is generated by the backend and must be unique.
- BR-02: A new Ticket begins with Current Status 'New'.
- BR-03: Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication.
- BR-04: Ticket Summary and Description are required.
- BR-05: Attachments must be JPG/JPEG, PNG, WEBP, or PDF and under 5 MB per file.
- BR-06: Maximum active attachments is 5 per Ticket.
- BR-07: Removed attachments must be soft-removed and no longer downloadable or previewable.
- BR-08: Inactive Requesters must not appear in the Development Requester selector.
- BR-09: A Requester can only access, view, or manage attachments for their own tickets.

## 6. UI Specification Summary
- Establish the Zen Green Theme (Primary green #006B3C, Secondary green #0B7A46).
- Use reusable form components, badges, lists/cards.
- Screens: Application Shell (Header), Development Requester Selection, Create Ticket, My Tickets, Requester Ticket Detail.
- Support responsive behavior for Desktop, Tablet, and Mobile.
- See `ui-spec.md` for full details.

## 7. Data Changes
- Models: `Ticket`, `Attachment`, `Category`, `RelatedSystem`, `RequesterUser`.
- `Ticket` belongs to `RequesterUser`, `Category`, `RelatedSystem`.
- `Attachment` belongs to `Ticket`.
- Fields: `Ticket` needs `ticketNumber` (unique), `summary`, `description`, `requestedPriority`, `currentStatus`, etc.
- Soft-removal: `Attachment` needs an `isRemoved` or `deletedAt` field.

## 8. API Contract
- `GET /api/requesters`: Retrieve active Development Requesters.
- `GET /api/categories`: Retrieve active Categories.
- `GET /api/related-systems`: Retrieve active Related Systems.
- `POST /api/tickets`: Create a Ticket for the selected Requester.
- `GET /api/tickets`: Retrieve paginated Tickets for the selected Requester.
- `GET /api/tickets/:id`: Retrieve one owned Ticket.
- `POST /api/tickets/:id/attachments`: Upload an Attachment.
- `GET /api/tickets/:id/attachments`: Retrieve Attachment metadata.
- `GET /api/attachments/:id/download`: Download an active Attachment.
- `DELETE /api/attachments/:id`: Soft-remove an Attachment.
- See `api-spec.md` for full details.

## 9. Acceptance Criteria
- AC-01: Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.
- AC-02: Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.
- AC-03: Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned (403 or 404).
- AC-04: Given an active ticket, when the user uploads a 6th attachment, then the system returns an error.
- AC-05: Given an active ticket, when the user soft-removes an attachment, then it is no longer downloadable.

## 10. Definition of Done
- Implementation of all approved scope.
- Satisfaction of all acceptance criteria.
- Passing and traceable automated tests (Unit, API, UI, E2E).
- Conformance to data, API, UI, validation, and responsive specifications.
- Peer review completed via GitHub PR.
- No tests skipped or disabled.
- README setup and test instructions are current.

## 11. Assumptions and Decisions
- Assumption: Temporary `requesterId` can be sent via HTTP Headers (e.g., `X-Requester-Id`) for API calls to simulate authentication context.
