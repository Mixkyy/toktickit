# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
The goal of this sprint is to deliver a Requester-facing IT ticketing application with features allowing a user to select a simulated testing identity, create IT support tickets, upload attachments with soft-delete capabilities, view a list of their tickets with filters, and access individual ticket details.

## 2. Stakeholder Request Interpretation
The stakeholder needs an internal IT Service Desk platform where Requesters can submit, track, and manage their own tickets. For Lab 2, we simulate multi-user behavior using a Development Requester selector. The core flows include creating tickets with attachments, tracking them via a searchable dashboard, and viewing ticket details.

## 3. Scope
### Included
- Development Requester selection (simulated login).
- Create Ticket form with fields for Category, System, Summary, Priority, Description, and Attachments.
- My Tickets dashboard with search, filter, sort, and pagination capabilities.
- Ticket Detail read-only view.
- Attachment lifecycle (upload, download, soft removal).
- Backend and Frontend validation, business logic, and UI state management.

### Excluded
- Real authentication, login, passwords, and sessions.
- IT Staff dashboard and workflow (e.g. status changes or assigning).
- Ticket collaboration (comments, actions taken).

## 4. Functional Requirements
- FR-01: The system shall provide a dropdown to select an active Development Requester.
- FR-02: A selected Requester shall be able to create a ticket by filling out a validated form.
- FR-03: The system shall support uploading up to 5 attachments per ticket (max 5MB each, specific formats).
- FR-04: The system shall display a list of the Requester's own tickets.
- FR-05: The system shall filter tickets by status and category, and support keyword search.
- FR-06: The system shall display a read-only Ticket Detail view with attachment management.
- FR-07: The system shall allow soft removal of attachments requiring a reason string.

## 5. Business Rules
- BR-01: The official Ticket Number is generated by the backend and must be unique.
- BR-02: A new Ticket begins with Current Status New.
- BR-03: Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only.
- BR-04: Requesters can only view and manage tickets associated with their own ID.
- BR-05: Attachments are limited to JPG, PNG, WEBP, and PDF.
- BR-06: Removed attachments remain visible as metadata but cannot be downloaded.

## 6. UI Specification Summary
The UI follows the Zen Green Theme. It includes an application shell with navigation, a Create Ticket responsive layout, a data table for My Tickets, and a card-based layout for Ticket Detail. More details are specified in `ui-spec.md`.

## 7. Data Changes
- Added `Attachment` model linking to `Ticket` with fields for file metadata, `isRemoved`, and `removedReason`.
- Updated seed data to include 4 required categories and 6 related systems.

## 8. API Contract
REST API implemented for categories, systems, requesters, and ticket endpoints (`GET /api/tickets`, `POST /api/tickets`, `POST /api/tickets/:id/attachments`, `DELETE /api/attachments/:id`). Detailed in `api-spec.md`.

## 9. Acceptance Criteria
- AC-01: Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.
- AC-02: Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.
- AC-03: Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned (403 Forbidden).
- AC-04: Given an attachment over 5MB, when uploaded, the system rejects it with an error.
- AC-05: Given a user soft-deletes an attachment, a prompt appears to provide a reason, and the attachment is marked as removed.

## 10. Definition of Done
- Implementation of all approved scope.
- Satisfaction of all acceptance criteria.
- Passing and traceable automated unit, API, UI, and E2E tests.
- Setup and execution documented in README.
